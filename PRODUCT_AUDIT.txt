=== 08. PRODUCT REQUIREMENTS AND CONSTRAINTS ===
- Standalone FastAPI/PostgreSQL/SQLAlchemy/Alembic/React system deployable to Heroku; not a WordPress or WooCommerce plugin.
- WooCommerce remains the customer-facing storefront. PongoOS is the operational inventory layer.

- MVP authentication may be simple, but production must remain authenticated and registration controlled.
- Operational priority: correct inventory state and auditable transitions over feature breadth.

FINDING: BE-001
TITLE: Woo stock queue trusts caller quantity and sends non-atomically
TYPE: RISK
STATUS: CONFIRMED
SEVERITY: P1
CONFIDENCE: HIGH
OWNER: Backend/Integrations
EFFORT: L
AFFECTED AREAS: WooCommerce stock writeback queue, approvals, worker/manual send, storefront stock

PLAIN-LANGUAGE SUMMARY:
The stock queue can store a quantity supplied by a caller and later send that saved number without proving it still matches current Pongo inventory. Two senders can also attempt the same row before either records completion.

WHY THIS MATTERS:
Once writeback is enabled, a stale or crafted queued quantity can publish the wrong storefront stock even when Pongo's current local totals are correct.

IF NOT FIXED:
Retries, delayed approvals, internal API misuse, or concurrent workers can send stale/duplicate updates. Live risk is currently contained because production authority/writeback are disabled.

IF FIXED:
Every Woo stock update is derived from current authoritative local inventory and exactly one sender owns each attempt.

WHAT TO DO IN SIMPLE TERMS:
Make the server calculate quantity, re-check it immediately before sending, and atomically mark one queue attempt as in progress.

TECHNICAL DETAILS:
The request schema permits arbitrary `payload_json`; create stores it. Validation checks only for a `stock_quantity` key. Approval validates mapping, not current quantity. Send loads the row normally and transmits the stored body; the separate revalidate operation is optional rather than part of send.

EVIDENCE:
backend/app/schemas/woocommerce.py:377 onward; backend/app/services/woocommerce_writeback.py:371-482 and 435-560; production `/ready` confirms authority/writeback false.

TECHNICAL REMEDIATION:
Remove quantity/body from public create input or ignore it. Generate the payload from current sellable stock and mapped Woo identity. In one transaction, lock the queue row, verify eligible status/approval, recompute quantity, record an attempt token and `sending` state, then perform the remote call with deterministic retry semantics. On completion, conditionally transition the owned attempt.

MIGRATION / ROLLOUT NOTES:
May require queue status/attempt columns and an index. Add nullable fields first, deploy compatible readers, migrate pending rows by revalidation, then enable atomic claim. Do not enable production authority during rollout.

VERIFICATION:
PostgreSQL tests must prove: a forged body is ignored/rejected; changing local stock after queue creation sends the recomputed value; two concurrent senders result in one remote attempt; retry after ambiguous failure is visible and safe; disabled authority prevents sending.

DEPENDENCIES AND ORDERING:
Requires a green PostgreSQL gate and consistent stock locks. Complete before SYS-003 authority promotion.

FINDING: BE-002
TITLE: Generic item writes expose Woo-owned identity fields
TYPE: DEFECT
STATUS: CONFIRMED
SEVERITY: P1
CONFIDENCE: CONFIRMED
OWNER: Backend/Data
EFFORT: M
AFFECTED AREAS: Item create/update, Woo refresh/remap, order matching, writeback mapping

PLAIN-LANGUAGE SUMMARY:
Normal item create and edit requests can directly change WooCommerce identity and snapshot fields that are supposed to be controlled by synchronization/remapping.

WHY THIS MATTERS:
These identifiers decide which storefront product or variation an inventory item represents. A generic edit can silently redirect sync or writeback to the wrong product.

IF NOT FIXED:
Internal clients can create duplicate mappings or overwrite Woo-owned values outside the reviewed remap workflow, causing order matching and refresh ambiguity.

IF FIXED:
Pongo-owned fields remain editable while Woo-owned identity changes only through explicit, validated synchronization/remap operations.

WHAT TO DO IN SIMPLE TERMS:
Remove Woo-owned fields from normal item forms/APIs and require the dedicated remap workflow for identity changes.

TECHNICAL DETAILS:
Item create/update schemas expose Woo product/variation and snapshot fields. The item update route blocks stock quantities but not these fields, and the service applies provided fields generically. The model does not prove uniqueness of the product/variation identity pair.

EVIDENCE:

=== 17. CROSS-CUTTING RISKS AND OPPORTUNITIES ===
1. The optimization architecture is proportionate. Existing SQL pagination, request cancellation, immutable caching, metric caching, and report jobs address real bottlenecks without adding a new service. Preserve this bias toward measured, local fixes.
2. Cache invalidation is intentionally broad. A single metric version invalidates all dashboard/insight namespaces and serializes version changes on one row. That is simple and appropriate for current single-organization volume; split versions by domain only if PostgreSQL lock/rebuild measurements show contention.
3. One worker handles operational sync, reports, history, and metric warming in priority order. Priority protects queued operational work before starting a report, but a report already running can occupy the single worker. Add worker separation only if measured report duration delays operational freshness.
4. Item import matching is set-based and memory/response sizes are bounded, but persistence and audit creation remain per row. Batching is the next likely backend improvement only if production PostgreSQL timing for real import sizes misses the agreed budget; background import processing is not justified by current local results alone.
5. Report data is stored three ways in PostgreSQL: JSON payload plus CSV and PDF binary artifacts. No formal cleanup/retention path was found for report runs/jobs. Define a business retention policy before history volume affects database size, backups, or the linear matching scan; do not delete audit evidence without product/legal approval.
6. The item data-completeness endpoint performs roughly one total count plus one count per missing-field predicate. It is the smallest immediate query optimization candidate: one conditional aggregate can calculate the same counts in one round trip, followed by focused API parity tests.
7. The main bundle remains large, but raw chunk size is not sufficient proof of slow user experience. Measure cold/warm startup and interaction timing on actual phones before splitting the 13k-line application or introducing more build abstractions.
