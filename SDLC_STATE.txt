=== 05. SCOPE, NON-GOALS, CONSTRAINTS, AND ASSUMPTIONS ===
IN SCOPE: phone camera scanner entry points on Items/Inventory; open-order query and deterministic driver assignment; missing-address reporting; keyless Google Maps URL construction; native share/clipboard fallback; responsive UI; tests and docs.
NON-GOALS: configuration changes, embedded map tiles, paid Google Routes API, traffic-aware optimization, server-side geocoding/address correction, route persistence, dispatch tracking, driver accounts, proof of delivery, WooCommerce writes, and stock changes.
CONSTRAINTS: Frontend receives no map credentials. Google Maps URLs have mobile waypoint limits, so long routes must be segmented. Existing completed-order route records remain available as a separate historical workflow.
ASSUMPTION: Operational open orders are the existing non-historical Woo processing/FooSales set and shipping address fields are the delivery authority.

=== 06. SYSTEM, JOURNEY, AND DATA MAP ===
Scanner journey: Items or Inventory -> Scan code -> rear camera or manual code -> existing local search -> matching item results.
Route journey: Routes -> default warehouse/start + driver count -> POST /api/routes/open-orders/plan -> one read-only operational order query -> address validation -> postal-area sort -> balanced driver groups -> continuous Google Maps URLs -> open/share.
Data boundaries: Order/customer/address snapshots travel from authenticated Pongo backend to the authenticated frontend. They are not sent to Google by the backend; Google receives addresses only when staff opens or shares a generated URL.
