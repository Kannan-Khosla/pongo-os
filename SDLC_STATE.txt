=== 03. PRODUCT VISION, USERS, AND SUCCESS METRICS ===
Primary users are Pongo warehouse staff and delivery coordinators using desktop, iPhone, or Android. Success means a scanned code immediately runs the current Items/Inventory search, and every routable open order appears exactly once in a visible driver plan. Staff can change driver count, optionally return to the warehouse, and share working Google Maps links without configuring map credentials.
Stock CSV success means staff can export/edit a CSV, preview exact per-location quantity changes, and commit valid rows without manually adjusting each item; every changed quantity remains auditable and allocated stock remains system-controlled.
Demo success means a prospect can sign in, browse all major workspaces with credible fictional data, and cannot read or change production records or access external integrations.
Subscription success means staff can see which sold products have active subscriptions, what quantity is next due, and whether current Pongo sellable stock covers the coming 30 days without opening phpMyAdmin.

=== 06. SYSTEM, JOURNEY, AND DATA MAP ===
Scanner journey: Items or Inventory -> hardware/rear-camera/manual code -> as-entered plus one-leading-zero barcode candidates -> exact/unique local match -> current search results; Enter then dismisses suggestions until editing resumes.
Manual stock journey: Inventory action -> choose location -> enter final quantity -> old/new/difference/allocated preview -> optional confirmation reason -> one idempotent audited adjustment -> totals/FIFO/configured writeback follow existing services.
Route journey: Routes / Live Planner -> select open orders -> either map the selection for one equal-time driver or choose the full driver/zone plan -> POST /api/routes/open-orders/plan with explicit order IDs -> exactly-once assignment/unassigned reasons -> in-app stop overview -> continuous Google Maps URLs -> open/share. Routes / Completed Routes contains only the persisted completed-order workflow.
Data boundaries: Order/customer/address snapshots travel from authenticated Pongo backend to the authenticated frontend. They are not sent to Google by the backend; Google receives addresses only when staff opens or shares a generated URL.
Stock CSV journey: Items -> Import CSV -> Override stock levels -> upload/map columns -> review current/new/variance -> confirm -> one audited stock adjustment -> results/history. Quantity authority is the selected active inventory location; item totals remain derived by the existing location inventory service.
Demo journey: operator creates demo user -> prospect signs in -> auth response identifies mock/read-only scope -> global header shows the Mythodus lockup on every workspace -> protected request session switches to the seeded demo database -> existing pages render fictional items, stock, orders, reports, and routes -> writes/integrations return a safe 403.
Live Woo orders journey: Dashboard -> Pongo backend requests exact `processing` rows -> validates `X-WP-Total` -> renders the isolated KPI and live rows; any upstream failure returns safe 503 and leaves all local Dashboard sections intact.
Picked completion journey: Open Orders -> complete a server-confirmed picked order -> validate active/actionable inventory lines only -> close locally without reducing stock again -> continue through the existing guarded Woo status/stock synchronization path.
Subscription journey: backend worker -> read all active Woo subscription pages -> validate every line -> atomically replace local snapshot -> exact variation/product or safe unique-SKU match -> join current Pongo stock -> Dashboard upcoming renewals, Insights drill-downs, and Sales by SKU immutable evidence. On failure, keep and label the last complete snapshot.
Order status journey: Dashboard -> backend-only live Woo `processing` list -> open one row -> reconcile and display that exact Woo order -> POST an idempotent target `completed` or `cancelled` action -> re-fetch exact Woo order -> apply guarded local completion/cancellation -> existing writeback queue -> refresh live rows. The Dashboard GET never changes local allocations or audit data.
Substitution journey: Open Orders detail -> choose an unprocessed line -> search/select an active mapped replacement -> confirm reason -> lock and release original allocation -> retain original Woo identity -> set effective Pongo item -> FIFO allocate replacement -> pick replacement -> completion absolute-syncs original and replacement stock, without editing the Woo order line.
Completed recovery journey: Completed Orders search -> view/reprint at any time -> eligible completed-without-picking action -> audited local recovery state -> revalidate/allocate -> existing picker and stock movement -> leave Woo status completed.
Item repair journey: Items -> Import items -> Repair item data and locations -> upload complete repair CSV -> map Pongo ID/Brand/Unit cost/target warehouse/target location -> validate all 1,348 rows -> review relocation and deferral totals -> type REPAIR -> one locked transaction -> paired transfer movements and import history -> rerun only after deferred allocations clear.
