PLAIN-LANGUAGE SUMMARY:
The app and supporting exports use “unmatched” for different problems. A legacy SKU absent from an old Pongo export, a Pongo item without a Woo ID, a current Woo product absent locally, and an order line not linked to an item are not the same thing. Treating them as one list makes the product catalog look far more broken than it is and encourages duplicate creation.

WHY THIS MATTERS:
Inventory identity is the basis for stock, allocation, picking, reporting, and Woo writeback. Operators need to know which direction a gap goes and whether the safe action is create, map, alias, archive, or repair an order line.

IF NOT FIXED:
Staff can create duplicates for existing products, import stale quantities, or attempt stock synchronization when only historical order-line state is wrong. Support will continue to reconcile contradictory counts manually.

IF FIXED:
One screen states the current Woo gap, local-only items, legacy-only records, conflicts, and repairable order lines separately. Every row has a match method, reason, and next action.

WHAT TO DO IN SIMPLE TERMS:
Replace the generic “unmatched” count with a read-only reconciliation preview. Auto-accept only exact Woo identity and exact normalized SKU. Present barcode, leading-zero, and title matches for approval. After catalog commit, repair safe order lines and show the result.

TECHNICAL DETAILS:
The allocation badge is derived from OrderItem.matched_status rather than catalog existence. Catalog commit creates/maps InventoryItem rows but does not revisit OrderItem. The `unmatched_local_items` metric counts local InventoryItem rows with no Woo product ID, which is the opposite direction from “Woo product missing locally.” The old-file set difference also includes aliases and multi-location rows.

EVIDENCE:
Production read-only evidence: 1,313 current Woo eligible SKU records, 1,308 local mapped items, 1,307 shared identities, six current Woo-only identities, and one local identity outside the current eligible Woo set. Active processing orders had 134 matched positive-quantity lines and zero unmatched; old completed/cancelled/failed rows retained unmatched history. Screenshot SKUs 37824, 454311, 471968, and 671957 exist with exact Woo IDs and current active matched lines. CSV evidence: 1,532 legacy exact SKUs versus 1,307 old enrichment SKUs, 1,303 overlap, 229 legacy-only, and deterministic alias cleanup to 205 identities. Code: frontend/src/App.jsx:10003-10018 and 12318-12326; backend/app/services/allocations.py:291-302; backend/app/services/woocommerce_sync.py:81-184 and 493-496.

TECHNICAL REMEDIATION:
Add one server-side reconciliation preview response with directional categories and stable row reasons. Reuse current catalog/remap services. Extract exact-identity OrderItem repair from manual remap and invoke it after successful catalog map/create for NULL/unknown/unmatched rows; leave conflict and protected history manual. Run FIFO allocation once after the batch. Update labels and counts without adding a second catalog subsystem.

MIGRATION / ROLLOUT NOTES:
No catalog data mutation until Woo access is Read only and a verified backup exists. Deploy preview first. Rehearse commit on a restored production copy. The one-time order-line backfill must include SQL NULL match status and preserve picked, fulfilled, stock-reduced, or otherwise protected lines for review.

=== 17. CROSS-CUTTING RISKS AND OPPORTUNITIES ===
Focused 2026-08-14 priorities:
1. Do not build a new generic import engine. Reuse the existing catalog, remap, identifier, adjustment, lock, idempotency, movement, and audit paths; add only the missing shared resolver, repair step, and inbound baseline direction.
2. The six live Woo-only products are the immediate catalog delta. The 229 legacy-only SKUs are a disposition queue, not a create queue.
3. Read & write is operationally acceptable only after recovery equality checks. During reconciliation it converts a local zero/stale item into storefront risk.
4. Two live Woo quantities are -1. Treat them as explicit upstream anomalies; do not weaken Pongo's nonnegative constraints to ingest them.
5. A full background-processing system is not justified. The current catalog size completed a read-only full pull in minutes; use synchronous reviewed work unless measured production commit time exceeds the maintenance window.

1. The optimization architecture is proportionate. Existing SQL pagination, request cancellation, immutable caching, metric caching, and report jobs address real bottlenecks without adding a new service. Preserve this bias toward measured, local fixes.
2. Cache invalidation is intentionally broad. A single metric version invalidates all dashboard/insight namespaces and serializes version changes on one row. That is simple and appropriate for current single-organization volume; split versions by domain only if PostgreSQL lock/rebuild measurements show contention.
3. One worker handles operational sync, reports, history, and metric warming in priority order. Priority protects queued operational work before starting a report, but a report already running can occupy the single worker. Add worker separation only if measured report duration delays operational freshness.
4. Item import matching is set-based and memory/response sizes are bounded, but persistence and audit creation remain per row. Batching is the next likely backend improvement only if production PostgreSQL timing for real import sizes misses the agreed budget; background import processing is not justified by current local results alone.
5. Report data is stored three ways in PostgreSQL: JSON payload plus CSV and PDF binary artifacts. No formal cleanup/retention path was found for report runs/jobs. Define a business retention policy before history volume affects database size, backups, or the linear matching scan; do not delete audit evidence without product/legal approval.
6. The item data-completeness endpoint performs roughly one total count plus one count per missing-field predicate. It is the smallest immediate query optimization candidate: one conditional aggregate can calculate the same counts in one round trip, followed by focused API parity tests.
7. The main bundle remains large, but raw chunk size is not sufficient proof of slow user experience. Measure cold/warm startup and interaction timing on actual phones before splitting the 13k-line application or introducing more build abstractions.
